# 300M / 3B：受限测速后的正式配置

日期：2026-10-25。旧 300M 实验 `20261025_140717` 已按用户要求在第 1,155 步正常停止并清空数据盘中的权重和日志。旧 100M 模型、全部语料、预算历史和小型操作记录均保留。旧时间戳标记为 `cleared`，启动器会拒绝再次使用它。新配置从随机参数开始，不恢复已删除的旧权重。

## GPU 实测与选择

用户授权助手代跑受限短测，正式长跑仍由用户启动。三组串行各跑 24 步，总墙钟约 **159.29 秒**；全程最多 360 秒，每项最多 180 秒。每步均为 32,768 Token，BF16、1024 上下文、相同 303,350,784 参数结构。稳态吞吐取第 6 到 24 步的 Token/时间增量，排除初始化与末尾保存；完成后每组 3.64 GB 的 checkpoint 均已删除，只保留配置、指标和报告。未进行最终 test 评测。

| Micro batch × 累积 | 激活重算 | Token/s | Peak allocated | Peak reserved |
| --- | --- | ---: | ---: | ---: |
| **8 × 4** | **关闭** | **31,674** | **19.65 GiB** | **20.72 GiB** |
| 16 × 2 | 关闭 | 27,371 | 33.82 GiB | 35.56 GiB |
| 16 × 2 | 开启 | 21,351 | 12.25 GiB | 14.74 GiB |

选择 **8×4、关闭激活重算**。16×2 在这次测试中占用更多显存且更慢；原因的独立占比仍需 profiler，不能猜测为显存虚拟化或指定内核问题。本次按实测吞吐选择，要求预留显存同时不少于总量的 15% 和 6 GiB，选中方案的 Torch 显存余量约 26.67 GiB。更高显存占用不自动带来更高吞吐。

这些是短测结果，不是全程性能保证，也不用于判断模型能力。短测没有经过第 500 步的首次验证/保存周期。按约 31,674 Token/s 粗算，30 亿处理 Token 的纯训练约 **26.31 小时**，考虑验证、保存和资源波动可先按 **27–30 小时**准备，正式运行覆盖完整周期后再更新。单卡实际波动可能超出该估计，不能据此保证完成时间。

报告：远程 `runs/benchmark_300m_20261025_150335/results.json`，本地 `tmp/pretrain/memory_benchmark_final.json`。新启动器和测速保护逻辑远程 CPU **43 passed**；核心 `src/llm_lab` 指纹与旧 100M 相同。

## 追加 8×8 对比

用户随后要求再测 8×8，已完成 `accumulation64k` 受限对比，耗时约 **95.76 秒**。8×4 跑 24 步，8×8 跑 12 步，两组都处理 **786,432 Token**。稳定窗口分别为 step 6→24 与 3→12，都使用 **589,824 Token**；两组各记录 12 条指标，日志开销也按 Token 对齐。两者均关闭激活重算，实际 micro batch 都是 8。

| 配置 | 每次更新 Token | 稳定 Token/s | Peak allocated | Peak reserved |
| --- | ---: | ---: | ---: | ---: |
| 8×4 | 32,768 | 31,904 | 19.65 GiB | 20.72 GiB |
| 8×8 | 65,536 | 32,090 | 19.65 GiB | 20.72 GiB |

8×8 本次点估计只快 **0.584%**，而前后两次 8×4 短测本身相差约 **0.725%**。这不是统计置信区间，但说明现有短测不足以确认 8×8 有稳定收益。数值排序器会把点估计最高的 8×8 列在前面；工程选择仍保留 **8×4**，因为 8×8 将有效 Batch 再翻倍，改变优化轨迹，却没有展示明显的吞吐改善。原正式配置 `20261025_150858` 未修改，也未启动长跑。

梯度累积顺序执行相同 micro batch，主要改变 optimizer 更新频率，不会把 8 个 micro batch 的激活同时保存在显存，因此本次峰值显存相同。若未来采用 8×8，为保持约 3B Token，应另建 45,777 步、warmup 750、每 250 步验证/保存的计划，不能沿用 91,553 步而将训练量无意翻倍；本次只测试，没有自动切换正式计划。

原始报告位于远程 `runs/benchmark_300m_20261025_151750/results.json`，本地 `tmp/pretrain/memory_benchmark_accum_handoff_latest.json`；本次追加保护测试远程 CPU **19 passed**。两组测试权重均已删除，保留完整指标和报告。

## 用户执行命令

先加载这次新的环境，做同一正式计划下的 32 步检查；它同时验证在线监控、实际正式输出和保存恢复，不能改成 `--max-steps 32`：

```bash
source /root/autodl-tmp/model_training/runs/configs/pretrain_300m_3b_20261025_150858.env
.venv/bin/python scripts/train_300m.py check --config "$RUN_CONFIG"
.venv/bin/python -u scripts/train_300m.py probe --config "$RUN_CONFIG" --steps 32
```

32 步正常退出后，再后台继续同一实验：

```bash
nohup .venv/bin/python -u scripts/train_300m.py resume \
  --config "$RUN_CONFIG" >> "$RUN_LOG" 2>&1 < /dev/null &
echo "训练 PID: $!"
tail -f "$RUN_LOG"
```

`tail` 中 `Ctrl+C` 只停止查看。要停止训练，对打印的 PID 发 `kill -INT PID`，等 `summary.status=signal_stop` 后再操作实例。以后恢复仍 source 原来的 `20261025_150858.env`，使用 `resume`；不要重新 prepare 或生成新时间戳。

未来新实验可以用 `scripts/train_300m.py prepare --template configs/pretrain/300m_3b_optimized.json` 创建新时间戳。本次已准备好，直接使用上面的新环境即可。启动器支持固定 3B 目标下的 16K/32K Token 更新计划，检测现存训练进程、GPU 占用、磁盘和预算，并在训练全程持项目排他锁。
