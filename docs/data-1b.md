## 目标与版本边界

新数据版本的训练容量至少为 **中英文各 500M Token，总计至少 1B**，按冻结 Tokenizer 编码后的有效 Token 计数，包含文档末尾 EOS。构建上限与最小容量分开配置，避免完整文档的尾部余量导致最小值无法达到；当前配置为每种语言最多 550M、至少 500M。

固定使用 Wikipedia `20231101` 快照和 revision `b04c8d1ceb2f5cd4588862100d08de323dccfbaa`。复用旧训练分区拟合的 32000 词表 BPE，校验并保存它的原始 SHA256，不重新用新验证/测试文本拟合 Tokenizer。

这里的 train-only 指旧原始划分的拟合历史。本次旧原始 train hash 与已保护 holdout 原始/转换 hash 的三项历史交集统计均为 **0**；范围仅限报告中的保护集合，不是全体历史 train 先转简体后的近重复证明。不能据此宣称“新转换后的 holdout 从未以等价文本参与旧 BPE 拟合”。

**中文分区统一使用官方 C++ OpenCC Python binding 的 `t2s` 转换。** 流程为：原文 → 原有 Unicode/空白规范化 → 中文繁转简 → 质量过滤/哈希/去重 → 固定 BPE 编码。`OpenCC==1.4.2` 官方 Linux wheel 已核验 SHA256 并安装到远程项目环境；转换的包版本、配置、词典、native binary 与算法身份已写入正式数据清单。原始 raw 保留繁简混合原文和来源，用于回溯；不把转换后的内容覆盖回原始文件。

这里的 `t2s` 使用本项目 `bounded_fixed_point` 策略，最多调用 8 次官方转换；只有相邻两次输出相同才返回，发现循环或达到上限仍未稳定就失败。该策略和上限写入 provenance v2，不能把单次 OpenCC 的输出误当作必然幂等的最终文本。英文原样返回，`none` 模式不加载 OpenCC。

该规则作用于标记为 `zh` 的中文分区。英文分区与英文冻结评测保持原样。简体字转换并不等同于重写地域词汇，也不保证模型生成永远不会出现词表中的繁体字。

## 两个阶段及当前入口

逐分片获取入口：

```bash
.venv/bin/python -m llm_lab.data.acquire_stream --config configs/data/acquire_wikipedia_1b.json
```

已完成的获取运行可使用相同配置加 `--resume`，恢复前校验已提交 raw 分片的大小和 SHA256；失败下载支持本步骤自己的部分文件续传。只有完整提交的 `raw/*.jsonl` 暴露给下游；`.part` 和未完成事务不能作为输入。SIGKILL 可能遗留 writer lock，必须确认旧进程结束再处理，不能并发启动两个 writer。

获取配置当前选择英文 8 个、中文 6 个固定 Parquet 分片，各自保存路径、大小和完整 SHA256。两种语言按轮询方式获取，限制每语言原始文本字节、全部 JSONL 字节和文档数；这些上限与压缩 Parquet 下载量分别计量。达到获取上限只表示此步骤结束，不能代替下游 500M/语言的容量验收。

本次制备使用独立配置，不能沿用旧的 30M Token 制备配置。以下保留本次入口；正式输出目录已经存在，不应重复执行覆盖。未来重建须先为配置选择新的输出目录：

```bash
cd /root/autodl-tmp/model_training
CUDA_VISIBLE_DEVICES="" TOKENIZERS_PARALLELISM=true RAYON_NUM_THREADS=8 \
  .venv/bin/python -m llm_lab.data.streaming_prepare \
  --config configs/data/prepare_wikipedia_1b.json
```

该步骤采用 SQLite 磁盘索引和有界批编码，不把全量文档或全部 Token 数组保存在内存中。当前 `encoding_batch_size=64`、`encoding_batch_max_bytes=4194304`，按至多 64 篇/累计 4MiB UTF-8 输入分批；超过字节阈值的单篇必须独占批次，既有文档质量/长度限制继续生效。这是批次输入边界，**不是 Python、Tokenizers、SQLite 或整个进程的 RSS 上限**。编码结果仍按文档原顺序追加 EOS、检查整篇 Token 配额并写 bin。

`TOKENIZERS_PARALLELISM`、`RAYON_NUM_THREADS` 和 CPU-only 变量只作用于该命令的进程，未为此修改全局 `scripts/env_remote.sh`；它们不能使仍为串行的清洗/SQLite 阶段自动变成八线程。本次完成情况由正式 manifest 和独立验收报告确认。

制备在开始时固定完成 JSONL 的输入列表、大小和 SHA256，并将每个 raw 文件与获取清单中的记录绑定，再追溯到固定 Parquet SHA256。逐行 `source_revision` 必须符合固定版本；新 raw 不得通过显式 `split=train` 覆盖稳定的源 ID 分区。

网络、平台已有系统 CA 和官方源的使用方式见 [数据指南](data-guide.md)；网络变量只作用于获取进程，避免影响后续 W&B 连接。

## CPU 优化的证据与范围

`normalize_text` 的类别过滤已换为按当前 `unicodedata` 表惰性生成的“允许范围否定字符类”，不硬编码 Unicode 黑名单。完整 Unicode（包括 surrogate）、混合空白/组合字符及二次规范化测试均与原实现严格一致；NFC、CRLF、逐行空白、质量过滤、哈希与去重顺序未改。英文仍保留原有的两次规范化，不能因看似重复就删除第二次 NFC。

远程各 1,000 篇中英文样本的双次规范化计时，英文约 **2.95×**、中文约 **3.74×**；这是清洗函数样本，不是整套制备提速。独立的 Tokenizer 单篇/批量编码样本报告约 **4.62×**，8,000 次逐文 Token ID 对照全部相同，逐文 EOS/整篇 cap 模拟一致；计时不包含清洗、OpenCC、SQLite 与正式 bin 落盘。这两项加速不能相乘后当作全流程加速。

## 冻结评测的简体迁移

旧验证集和测试集的源 ID 保持冻结；新扫描文档继续按既定 seed/source ID 分区，新的验证/测试候选只进入隔离账本，不加入原有评测分区。

本次语言规范变化需要明确区分两种操作：

- **英文验证/测试**：按旧 manifest 校验原始 Token 文件的大小、数量和 SHA256，再复制，要求字节不变。
- **中文验证/测试**：从旧 `documents.jsonl` 找回确实构成冻结 Token 文件的完整文档，先用旧 BPE 和 EOS 复算原始内容，与旧 bin 的数量/哈希核对；然后按相同文档顺序做 `t2s`，再用同一个 BPE 编码并生成新的 bin。

中文旧 Token 文件不能直接复制后宣称“已转换”。缺文档、文档顺序无法证明、旧来源校验失败或 Tokenizer 不一致时，应明确失败，不静默退回繁简混合评测。

隔离索引同时保护旧源 ID、原文规范化哈希和转换后的规范化哈希。繁转简会把不同原文映射到相同文本，新 train 中的这种别名也必须从冻结 holdout 排除。若冻结验证/测试之间转换后发生碰撞，保留源 ID 与跨分区去重会产生冲突，应报告并停止；不能悄悄移动或删除测试文档。

旧审计还包含当时因 Token 预算未写入 bin 的 holdout 文档。本次独立验收已找齐全部受保护中文 holdout 原文，确认源 ID、原始 hash 与转换 hash 均进入审计及索引，缺失数均为 **0**；活跃 train 候选与保护源/保护 hash 的交集均为 **0**。英文 holdout 字节不变；中文原始 bin 重建和新简体 bin 重建均通过。

**新中文评测文本已经变化，旧繁简混合评测 Loss 与新简体评测 Loss 不能直接横向比较。** 新数据 manifest、转换版本和评测身份需要一起记录；100M 与 300M 的新实验应使用同一套已验收数据版本。

## 数据质量与容量验收

本次按以下门槛制备并完成独立验收；独立检查的范围和限制见下节：

1. 中英 train 各自达到至少 500M Token，不能用英文超额弥补中文不足；来源耗尽仍不足时明确失败，不能复制数据凑容量。
2. 旧 BPE 文件哈希不变，仍具有明确的 train-only 来源；中文文本先转换，再进行哈希、去重与编码。
3. 英文 holdout 字节不变；中文 holdout 的文档源、顺序、原始重建证明、转换后数量与哈希均可追踪。
4. train 与冻结 holdout 的源 ID、原哈希和转换哈希不相交；新的非训练候选保持隔离。归一化/转换引发的碰撞有审计记录。
5. 每个 Token 流使用 little-endian uint32，实际字节数等于 `token_count × 4`，SHA256 匹配，完整文档以合法 EOS 结束。
6. 按语言记录扫描、过滤、重复、保护组排除、编码文档数、Token 数和容量不足原因。清洗候选数不能当作最终写入 train 的文档数。
7. 最终 `manifest.json` 在全部检查通过后原子发布；只有部分 bin、`cleaned.jsonl` 或阶段状态不能算作完成的数据集。

正式 Token 数已由最终 bin 的数量、大小、合法 ID 和 SHA256 验收，不再用此前约 4.1 原文字节/Token 的换算判断容量。

此前中文抽样外推约 **714.27M Token** 只保留为历史估计；本版实际写入受每语言 550M 上限和整篇文档边界约束，以已发布表格为准。raw 文档数、原文字节与 JSONL 总量保持原获取结果不变。

## 独立验收的范围与限制

86 项检查覆盖获取来源链、全部流的大小/SHA/ID、固定 BPE/OpenCC 身份、审计/cleaned/索引指纹、保护集合隔离及冻结评测原文/顺序/新旧 bin 重建。制备器对全部 **1,384,748** 篇 raw 中文做过幂等检查；独立验收另行复查的是 **55** 篇实际写入中文 holdout，未独立重查所有 train 文本。

本次 `train_reencoded=false`：隔离查询覆盖最终活跃候选超集，但没有独立全量重编码 train 以证明每个 bin 位置到原文的映射。验收也不检查语义近重复、隐私、百科事实正确性或其他 Base 的训练历史；旧 BPE 历史交集为零仅限上述精确 hash 范围。六个 CPU 采样只验证读取接口，不验证模型能力；容量也不等于有放回训练的无重复覆盖。

目前制备实现明确不支持从未完成输出目录续跑：失败后保留证据、拒绝覆盖，需审计后选择新输出目录。获取续传与制备续跑是两种能力，不能合并宣称任意阶段都能断点恢复。

## 内存、磁盘与扩容状态

已知实例 RAM 为 90 GB。制备按文档编码、Arrow 小批读取、SQLite 磁盘索引控制内存；仍需观察真实峰值，不能以 RAM 总量推断程序一定不会超限。

用户重启实例后，`statvfs` 已确认文件系统扩至 **70.0 GiB**；验收采集时可用 **28.717 GiB**。正式产物目录合计 **12,136,828,541 bytes**，包含 cleaned、audit、SQLite 索引、bin 和其他制备产物，不能只按 train 的约 4.4GB 估算空间。后续仍以 `df`/`statvfs` 实时可用空间作为写入条件；本流程不自动扩容或清理用户数据。

峰值空间需要同时容纳：新增 Parquet 缓存、raw JSONL、cleaned 候选文本、SQLite/日志/临时聚合表、最终 uint32 流和转换后的 holdout。训练容量 1B Token 自身约占 4 GB；若达到各 550M 的上限，train bin 合计可接近 4.4 GB。不能仅按这 4–4.4 GB 推断总盘空间需求。

获取配置限制 raw JSONL 至多 7 GB、每语言原文最多 3 GB；制备清洗文本上限为 6.5 GB。8GiB 磁盘水位继续保留。后续 Checkpoint、模型缓存与 300M 实验还会增加占用，不在本次数据容量证明中一并保证。

## 语料容量与训练计数
